# 下一阶段开发指导方案

更新日期：2026-07-11

## 1. 阶段目标

下一阶段不继续堆叠页面功能，而是把已经可用的 Web 产品整理成可长期演进的系统，为后续 Android 独立界面提供稳定基础。

目标按优先级排序：

1. 保证训练事实、计划、状态和同步不会丢失或被静默覆盖。
2. 固化身刻、计时器、Worker 和未来 Android 共用的数据契约。
3. 拆分当前单体代码，建立可测试、可迁移、可回退的工程结构。
4. 保留 Web 端已经确认的交互和视觉基线，只处理明确存在的问题。
5. Android 共用领域模型和同步协议，但重新设计信息架构和界面，不做桌面版缩放。

## 2. 当前基线

### 已经成立的能力

- 身刻和 `home-training-timer` 保持独立仓库和独立部署。
- IndexedDB 是本地第一写入点，D1 是共享云端副本。
- 身刻管理计划、日历、正式训练记录、身体状态和反馈摘要。
- 计时器管理动作执行、语音、常亮和 `timer_sessions`。
- `routine_templates` 已能由身刻导入并由计时器从云端读取、缓存和离线执行。
- Web 日历和桌面计时器已经形成可继续维护的产品基线。

### 必须优先解决的风险

- 本地脏记录可能在拉取云端记录时被静默覆盖。
- 计时器把部分云端文本直接写入 `innerHTML`，存在注入风险。
- `timer_sessions.actualSeconds` 目前可能包含暂停时间。
- 重置、退出或异常中断未稳定形成 `stopped` 会话事实。
- Worker 主要校验记录信封，没有完整校验实体内容。
- 已发布计划和 routine 的不可变规则尚未由代码强制执行。
- 单体文件过大，测试和持续集成不足。

## 3. 总体路线

全程分为 7 个工作包。每完成一个工作包必须输出一次进度报告，报告格式见第 8 节。

### 工作包 0：冻结基线与测试样本

目的：在结构调整前锁定现有行为，避免重构时破坏已确认功能。

交付物：

- 身刻关键流程样本：计划导入、日历优先级、训练保存、状态保存、同步冲突。
- 计时器关键流程样本：云端 routine、离线缓存、暂停恢复、中断、完成上报。
- Worker API 契约样本：查询、批量 upsert、越权、冲突、分页。
- 一组脱敏的固定测试夹具，不包含真实健康数据。
- GitHub Actions 基础流水线，至少运行静态检查和自动化测试。

验收门槛：

- 两个仓库都能在干净环境中运行测试。
- 当前关键行为有可重复验证的样本。
- 不修改用户数据，不进行数据迁移。

### 工作包 1：数据正确性与安全

目的：先处理会造成数据错误、事实错误或安全问题的缺陷。

身刻：

- 重写同步合并判断：本地 dirty 记录不得被云端静默覆盖。
- 关键实体出现并发修改时创建 conflict 状态，保留两份候选。
- 保存训练和保存状态分别关闭对应编辑区，互不清空草稿。
- 一天多条 `training_logs` 使用独立 ID，不再按日期覆盖第一条。

计时器：

- 所有云端可控文本通过 `textContent` 或安全节点创建，不使用不受控 `innerHTML`。
- 区分墙钟时长、暂停时长和有效训练时长。
- 完成、停止、重置和异常离开均写出语义明确的 session。
- 未完成会话恢复后不得重复上报。

Worker：

- 认证先于配置读取和业务查询。
- 对每种可写实体做结构、字段类型、长度和枚举校验。
- 拒绝越权实体和异常大 payload。

验收门槛：

- 离线编辑后再同步不会丢失本地修改。
- 暂停 5 分钟不会计入 `actualSeconds`。
- 中断流程可在身刻中看到 `stopped` 事实。
- 注入型文本只按纯文本显示。

### 工作包 2：共享 Contract v1 与版本治理

目的：让 Web、计时器、Worker 和 Android 对同一数据含义达成机器可校验的约定。

交付物：

- JSON Schema：所有共享实体、记录信封和 `coach_plan_patch`。
- OpenAPI：Worker 对外接口、错误码、分页和冲突响应。
- `contractVersion` 和兼容范围。
- `trainingType`、状态、routine execution mode 的统一枚举。
- 标准名称映射只负责展示，不改变内部 ID。

版本规则：

- 已发布 `plan_templates` 和 `routine_templates` 不允许原地改内容。
- 内容变化必须创建新版本和新 ID；旧版本保留供历史快照引用。
- `daily_plan_items` 保存确认时快照，不因模板升级而重写。
- `plan_adjustments` 追加保存，不使用每日期固定 ID 覆盖历史。
- 日详情只显示当前有效指导；历史调整可在专门历史入口查看。

验收门槛：

- 两个前端和 Worker 使用同一套 schema 测试。
- 老记录有兼容读取路径。
- 非法 patch 在预览阶段被拒绝，不进入本地库或云端。

### 工作包 3：工程拆分与可维护性

目的：在不改变用户界面的前提下拆分单体代码。

身刻建议模块：

```text
src/
  domain/        领域类型、归一化、优先级、建议规则
  storage/       IndexedDB、迁移、outbox
  sync/          API client、merge、conflict
  features/      calendar、records、metrics、plans、settings
  ui/            Web 组件和页面装配
  platform/      browser / Android adapter 接口
```

计时器建议模块：

```text
src/
  catalog/       routine 获取、缓存、名称映射
  engine/        step 展开、状态机、时钟
  session/       session 事实和上报
  adapters/      voice、wake lock、storage、cloud
  ui/            选择态、预览态、执行态
```

技术路径：

- 使用 Vite + TypeScript 管理构建和模块，不立即引入大型 UI 框架。
- 先抽纯函数和 adapter，再拆 DOM 渲染；每步保持可运行。
- CSS 按 token、layout、component、feature 分层。
- Worker 与前端共用生成后的 schema 类型，不复制枚举字符串。

验收门槛：

- 领域逻辑不依赖 DOM。
- 同步、推荐、计划归一化和计时状态机可独立测试。
- 页面行为和部署地址保持不变。

### 工作包 4：本地存储与同步 v2

目的：降低全量序列化和逐条网络操作的成本，形成可靠离线队列。

交付物：

- IndexedDB 按实体 store 存储，提供版本化迁移。
- 独立 outbox：记录待推送操作、重试次数和 baseRevision。
- 增量拉取游标、批量 upsert、分页查询。
- tombstone 保留期和清理策略。
- 冲突处理入口：使用云端、使用本地新版本、人工合并。
- 多设备配置档案继续只保存密文，增加设备撤销和档案轮换能力。

验收门槛：

- 普通保存不再重写整个本地快照。
- 1000 条记录下同步和首屏读取仍可接受。
- 断网、重连、重复请求和中途失败均保持幂等。

### 工作包 5：Web 信息架构与可访问性收尾

目的：只修复已经确认的问题，不重做成熟的桌面日历。

主要调整：

- “记录”统一为正式训练记录入口；计时器事实作为来源或详情层，不与正式记录并列成第二套历史系统。
- 嵌入计时器区分“选择/预览”和“执行”状态，减少双层应用感。
- 设置页把日常同步、设备迁移和危险操作分级。
- 趋势图按有效数据量和容器尺寸自适应，空数据不占巨大画布。
- 日期抽屉实现 dialog 语义、焦点锁定、Escape 关闭和焦点归还。
- 日历提供更高效的键盘导航，支持 `prefers-reduced-motion`。

验收门槛：

- 桌面核心流程不出现视觉回归。
- 键盘可完成打开日期、编辑、保存和关闭。
- 低对比度、焦点不可见和整页 `aria-live` 问题被消除。

### 工作包 6：Android 基础与独立移动界面

目的：复用领域与数据能力，重新设计移动端使用方式。

第一阶段只做基础，不在本阶段定稿视觉：

- Capacitor 容器和 Android 构建流水线。
- 复用 domain、storage contract、sync protocol 和 timer engine。
- 新建 mobile presentation，不直接复用桌面 7 列日历和右侧抽屉。
- Secure Storage 保存本地解密后的配置和令牌。
- 原生 adapter：屏幕常亮、TTS、前台服务、返回键、文件导入导出。
- 先定义手机核心任务：今日指导、开始训练、补状态、查看近期记录。

验收门槛：

- Android 与 Web 对同一测试数据得到相同业务结果。
- 断网可查看、记录和执行缓存 routine。
- 后台/锁屏计时行为符合 Android 平台约束。
- UI 不出现桌面布局缩放、横向挤压或嵌套滚动。

## 4. 跨工作包依赖

```text
基线测试
  -> 数据正确性与安全
  -> Contract v1
  -> 工程拆分
  -> 存储与同步 v2
  -> Web 收尾
  -> Android 基础
```

允许并行：

- Worker 校验与计时器 XSS 修复可以并行。
- Contract schema 与脱敏测试夹具可以并行。
- Web 可访问性检查可在工程拆分后半段开始。

禁止并行：

- Contract 未冻结前，不开始 Android 业务数据实现。
- 同步冲突未修复前，不进行本地数据库大迁移。
- 领域逻辑未抽离前，不引入 UI 框架重写页面。

## 5. 测试矩阵

| 层级 | 身刻 | 计时器 | Worker |
| --- | --- | --- | --- |
| 单元 | 归一化、优先级、趋势、patch | step 展开、状态机、有效时长 | 权限、校验、冲突规则 |
| 契约 | 所有实体读写 | routine/session | OpenAPI + JSON Schema |
| 集成 | IndexedDB + outbox + sync | cache + engine + upload | D1 migration + API |
| E2E | 导入计划到日历和记录 | 选 routine 到完成/中断 | 多角色端到端 |
| 离线 | 保存、刷新、重连 | 缓存执行、延迟上报 | 幂等重试 |
| 平台 | Desktop / Firefox / Chromium | iframe / standalone | 线上与本地环境 |

## 6. 发布与迁移策略

- 每次 schema 变化都包含 migration、兼容读取和回退说明。
- 新同步实现先用 feature flag 双写校验，再切换为主路径。
- 迁移前自动导出本地 JSON 备份，但不提交仓库。
- 发布顺序通常为 Worker 兼容版本 -> 两个 Web 客户端 -> 清理旧路径。
- Worker 必须先兼容新旧客户端，不能要求用户同时刷新所有设备。
- 任何可能删除记录的操作必须预览数量并二次确认。

## 7. 里程碑定义

- M1：事实可信。同步、计时、停止和安全问题解决。
- M2：契约稳定。共享 schema、版本规则和 API 契约落地。
- M3：代码可维护。单体拆分、CI 和核心测试覆盖完成。
- M4：同步可扩展。outbox、分页、批量和设备管理完成。
- M5：Web 完整。信息架构和可访问性收尾。
- M6：Android 可启动。共享领域层和独立移动呈现跑通。

## 8. 进度报告格式

每完成一个工作包，输出：

```text
总进度：X / 7
本阶段：名称
已完成：具体交付物
验证：自动化测试、手工场景、线上检查
兼容性：旧数据和旧客户端如何处理
遗留风险：尚未处理的问题
下一阶段：明确入口和前置条件
```

不以“代码已写完”作为完成标准。只有实现、迁移、测试、文档和回退方案全部满足，工作包才算完成。
