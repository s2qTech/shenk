# Mobile Strategy

## 结论

v2 不采用纯 PWA 作为唯一手机方案。

原因：

- 目标手机是小米/HyperOS，PWA 安装和桌面入口可能不可用或不稳定。
- 用户需要一个能像普通 App 一样打开的入口。
- 系统仍然需要电脑端访问，因此不能只做原生 Android。

推荐路线：

```text
同一套 Web 核心
  -> 电脑端网页
  -> Android APK 壳
```

## 首选方案：Capacitor Android 壳

Capacitor 可以把现代 Web 应用放进原生 Android 容器里。

优点：

- 不依赖小米浏览器或 Chrome 的 PWA 安装能力。
- 可以生成 APK，直接安装到手机。
- 仍然复用同一套 Web UI 和业务逻辑。
- 后续可接相册、文件、相机、通知、常亮等原生能力。
- 电脑端仍然使用同一套 Web 前端。

缺点：

- 需要 Android 构建环境。
- 更新 APK 比更新网页麻烦。
- 如果不用应用商店，需要手动安装新版 APK。

## 备选方案：Trusted Web Activity

Trusted Web Activity 可以把 PWA 放进 Android App 中打开。

不作为第一选择，原因：

- 它仍依赖浏览器能力。
- 如果手机上的浏览器能力不足，体验仍可能不稳定。
- 更适合已经稳定部署并满足 PWA 要求的网站。

## 备选方案：纯原生 Android

不建议第一版使用。

原因：

- 电脑端仍然要另做网页。
- AI、同步、日历、日志、趋势这些逻辑会被拆成两套。
- 开发和维护成本更高。

## 数据策略

Android 壳和电脑网页必须使用同一套数据结构。

第一阶段：

- Android 本地 IndexedDB。
- 电脑网页本地 IndexedDB。
- JSON 导入导出。

第二阶段：

- Supabase/Firebase 云同步。
- 手机和电脑登录同账号后同步。

## 权限策略

Android 壳可能需要：

- 相册/文件选择：上传运动截图。
- 定位：记录当天天气。
- 网络：AI 分析、天气、同步。
- 屏幕常亮：训练计时器。

权限必须按需请求，不在首次打开时一次性索取。

## 发布策略

第一阶段：

- 生成本地 APK。
- 用户手动安装。

第二阶段：

- 根据实际需求再考虑应用商店。
- 如果只是个人使用，不必上架。

## 设计约束

Android 壳不应改变产品形态。

它只是安装和权限容器：

- 不单独设计一套 Android 原生 UI。
- 不把业务逻辑写死在原生层。
- 不让手机端和电脑端功能分裂。
